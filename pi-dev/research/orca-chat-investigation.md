## Main findings

1. **Orca chat is a subprocess RPC integration, not terminal emulation.** It resolves a runnable `pi` (or configured literal program + prefix arguments), probes it with `--version`, then starts it with `--mode rpc` and pipes. Chat prompts and controls go over JSONL, not terminal keystrokes. A wrapper selected as `pi` receives these invocations too.
2. **There are multiple independent reasons to invoke Pi.** Host availability checks use the host home directory; workspace admission and actual chat launches use workspace/pinned chat directories; standalone model discovery runs a separate `--mode rpc --no-session` process in **host `homedir()`**. Thus “opening chat” is not necessarily one process invocation in one cwd.
3. **The normal version probe has a 5-second default, but a timed-out probe is `unknown`, not `tooOld`.** Admission permits `unknown`; the actual Pi launch only explicitly rejects `tooOld`. Catalog discovery deliberately removes the version probe's local timeout and RPC request/session timers, while still allowing outer cancellation/deadline ownership.
4. **Cwd and environment are different inputs.** Actual chat cwd is the workspace/pinned launch directory. The shell environment can be captured from an interactive login shell, but Orca does not evaluate the chat program as a shell command. An executable Bash wrapper still executes its own shebang and commands.
5. **Source supports a concrete wrapper interaction, not a diagnosis.** This repo's wrapper names a sandbox from `basename "$PWD"`, runs `sbx ls` before every forwarded invocation, and may create a sandbox before forwarding `--version` or RPC arguments. Home-directory probes could therefore select a different sandbox name than a worktree-directory launch. This does **not** establish that the reported “OMA” sandbox came from any particular probe.

Renderer routing chooses `structured-native-chat` only when explicit chat preference (or saved default) and support checks both pass; otherwise it chooses `terminal-tui`. Menu selection also tracks inventory/pending capability answers and explicit Terminal selection. Sources: [`src/renderer/src/lib/agent-session/launch/routing/agent-launch-routing.ts:12–60`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/renderer/src/lib/agent-session/launch/routing/agent-launch-routing.ts#L12-L60), [`src/renderer/src/lib/agent-session/launch/routing/agent-menu-selection.ts:38–60`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/renderer/src/lib/agent-session/launch/routing/agent-menu-selection.ts#L38-L60).

### Opening a tab does not necessarily acquire a child immediately

The create handler selects an **at-rest create** for fork, first-message, or clients advertising create-message capability. Commit then calls `host.create`, publishes the durable chat/tab, rather than using the legacy acquired `host.attach` path. Founding queues/performs a first message when provided; an empty create has a separate branch. Therefore do not equate visible tab creation with successful RPC startup or assume every empty tab immediately spawns its conversational Pi process. Sources: [`src/main/runtime/rpc/methods/structured-sessions/creation/structured-agent-session-create-handler.ts:101–123`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/runtime/rpc/methods/structured-sessions/creation/structured-agent-session-create-handler.ts#L101-L123), [`src/main/runtime/rpc/methods/structured-sessions/creation/structured-agent-session-create.ts:169–227`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/runtime/rpc/methods/structured-sessions/creation/structured-agent-session-create.ts#L169-L227), [`src/main/native-chat/agent-session-wire/acquisition/structured-agent-session-create-founding.ts:193–260`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/native-chat/agent-session-wire/acquisition/structured-agent-session-create-founding.ts#L193-L260).

When acquisition is needed, Pi's registration constructs `PiRpcSessionAdapter` with composed shared launch resolution plus Pi-specific resolution. `acquire` resolves launch, builds the spec, constructs `PiRpcSession`, tracks the connection, captures process identity, and cleans up failures; it rejects concurrent ownership or an earlier child whose exit is unproven. Sources: [`src/main/pi/rpc-runtime-registration.ts:15–29`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc-runtime-registration.ts#L15-L29), [`src/main/pi/rpc/rpc-session-adapter.ts:46–115`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/rpc-session-adapter.ts#L46-L115).

## 2. Binary discovery and Command settings

- Ordinary installed-agent detection is **path/file discovery**, not necessarily `pi --version`: it batches commands on local PATH, then install directories; configured overrides contribute their executable token. Pi's detection name is `pi`. Do not confuse the generic git/gh preflight version-probe helper with this installed-agent detection path. Sources: [`src/main/preflight/installed-agent-detection.ts:98–140`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/preflight/installed-agent-detection.ts#L98-L140), [`src/main/preflight/agent-command-detection.ts:13–44`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/preflight/agent-command-detection.ts#L13-L44).
- Structured chat resolution uses `env.PATH ?? env.Path`, and `HOME ?? USERPROFILE` for fallback install directories. Stock lookup prefers PATH, then known version-manager and system install directories, finally the bare name when unresolved. Known directories include NVM, Volta, asdf, fnm, mise, `.local/bin`, pnpm, Yarn and Bun. Sources: [`src/main/pi/rpc/launch/rpc-launch-resolution.ts:78–89`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch-resolution.ts#L78-L89), [`src/shared/shell/command-resolution/node-cli-command-resolution.ts:125–206`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/shared/shell/command-resolution/node-cli-command-resolution.ts#L125-L206).
- Explicit `agentCmdOverrides.pi` is parsed as a **literal program plus prefix argv**, not evaluated shell text. Shell interpolation/operators, inline environment assignments and divergent shell parses are rejected. Absolute executable paths and found bare program names are supported; relative executable paths containing separators are rejected. `~/` expansion is supplied explicitly, including prefix args. Sources: [`src/shared/agent-launch/startup/tui-agent-launch-command-override.ts:5–25`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/shared/agent-launch/startup/tui-agent-launch-command-override.ts#L5-L25), [`src/main/native-chat/agent-launch/structured-agent-command-resolution.ts:57–79`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/native-chat/agent-launch/structured-agent-command-resolution.ts#L57-L79), [`src/main/native-chat/agent-launch/structured-agent-command-resolution.ts:89–147`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/native-chat/agent-launch/structured-agent-command-resolution.ts#L89-L147), [`src/shared/shell/command-resolution/node-cli-command-resolution.ts:216–249`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/shared/shell/command-resolution/node-cli-command-resolution.ts#L216-L249).
- Although shared resolution has an Orca-managed-copy fallback for some agents, **Pi is not in the managed CLI registry** at this commit. Do not assume Orca bundles/replaces the Pi binary. Source: [`src/main/managed-agent-cli/managed-agent-cli-registry.ts:30–42`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/managed-agent-cli/managed-agent-cli-registry.ts#L30-L42).

## 3. Version probes and timeout semantics

`readAgentCliVersion` runs `[...prefixArgs, '--version']` with the supplied program/cwd/env. Defaults: **5,000 ms**, **4,096 output bytes**, kill on output limit, termination barrier enabled. An operation deadline can shorten the timeout; `timeoutMs: null` removes this local timeout. It combines stdout and stderr for version parsing. The parser extracts the first valid semver-like version, not a Pi-specific banner. Sources: [`src/main/agent-launch/preflight/agent-cli-version-probe.ts:56–103`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/agent-launch/preflight/agent-cli-version-probe.ts#L56-L103), [`src/shared/app-lifecycle/identity/app-version.ts:25–32`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/shared/app-lifecycle/identity/app-version.ts#L25-L32).

Results:

| Probe outcome | Version check | Consequence evidenced here |
| --- | --- | --- |
| Parsed version at/above minimum | `ready` | Launchable |
| Parsed version below minimum | `tooOld` | Chat admission refuses; actual launch throws installation error |
| Timeout, truncated output, nonzero exit, no parsable version | `unknown` | Admission permits; actual launch does not explicitly reject |
| Runner throws before start (unless operation cancellation supersedes) | `missing` | Admission is not launchable |

Sources: [`src/main/agent-launch/preflight/agent-cli-version-probe.ts:18–54`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/agent-launch/preflight/agent-cli-version-probe.ts#L18-L54), [`src/main/agent-launch/preflight/agent-cli-version-probe.ts:82–103`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/agent-launch/preflight/agent-cli-version-probe.ts#L82-L103), [`src/main/pi/rpc/launch/rpc-launch-resolution.ts:194–201`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch-resolution.ts#L194-L201).

Pi RPC minimum is **0.84.0**, because this integration requires `agent_settled`. Actual conversational launch **rechecks every launch**, even after prior admission, because the PATH binary may have changed. Limited-tool read-only sessions additionally require known version >=1.0.4 for `--no-mcp`; version >=1.5.1 enables the assumption that every prompt image is shrunk. Sources: [`src/main/pi/rpc/launch/rpc-launch-resolution.ts:73–76`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch-resolution.ts#L73-L76), [`src/main/pi/rpc/launch/rpc-launch-resolution.ts:194–215`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch-resolution.ts#L194-L215), [`src/main/pi/rpc/launch/rpc-launch-resolution.ts:261–264`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch-resolution.ts#L261-L264), [`src/main/pi/rpc/launch/rpc-launch.ts:94–115`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch.ts#L94-L115).

## 4. Actual conversational RPC spawn

### Arguments

`buildPiRpcLaunch` produces this ordering (optional groups shown in brackets):

```text
<resolved program> <configured prefix args>
  --mode rpc
  <extraArgs, if supplied to builder>
  [--append-system-prompt <instructions file>]
  [--skill <directory>]...
  [read-only tool flags]
  [--extension <background-work bridge file>]
  [--extension <bot-tools file>]
  [--session <existing session file> | --fork <source session file>]
```

Normal chat does **not** append `--no-session`. The standalone catalog does. The builder requires full access, validates conflicting print/mode/session flags and provider-without-model, and applies read-only tool restrictions where requested. **The real Pi launch-part return at this commit does not populate `extraArgs`; do not mistake builder capability for proof that every saved terminal Arguments string is appended to conversational Pi argv.** Model/effort have RPC setters (`set_model`, `set_thinking_level`). Sources: [`src/main/pi/rpc/launch/rpc-launch.ts:118–202`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch.ts#L118-L202), [`src/main/pi/rpc/launch/rpc-launch-resolution.ts:233–267`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch-resolution.ts#L233-L267), [`src/main/pi/rpc/options/rpc-options.ts:158–193`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/options/rpc-options.ts#L158-L193).

The background-work bridge helper writes an extension file under Orca user data (`pi-native-chat`), allocates a private probe-folder path and reclaims abandoned folders; **it is not another `pi` executable invocation**. Failure may leave chat launching without the bridge. Source: [`src/main/pi/rpc/background-work/rpc-background-work-bridge.ts:18–50`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/background-work/rpc-background-work-bridge.ts#L18-L50).

### Cwd, env and shell behavior

Shared composition resolves cwd once from the durable session record/workspace, then seals child identity; Pi's part is not allowed to choose a different cwd. The final build uses that cwd. Sources: [`src/main/runtime/agent-session/launch/structured-agent-launch-composition.ts:187–211`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/runtime/agent-session/launch/structured-agent-launch-composition.ts#L187-L211), [`src/main/runtime/agent-session/launch/structured-agent-launch-composition.ts:248–282`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/runtime/agent-session/launch/structured-agent-launch-composition.ts#L248-L282), [`src/main/pi/rpc/launch/rpc-launch.ts:176–201`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch.ts#L176-L201).

Environment flow:

## 7. Local wrapper interaction: facts versus inference

**Conditional source-derived implications, not reproduced outcomes:**

- **If Orca resolves this wrapper**, `--version` is not cheap by construction: it traverses `sbx ls`, may create a sandbox, then forwards `--version`. Whether that exceeds any budget depends on `sbx`, networking and sandbox state.

The wrapper supplies only `"$PWD"` and `/var/folders/_j` as positional paths to sandbox creation; their exact mount semantics are unverified. Source inspection does not prove those other paths are meaningful in the sandbox, nor that returned sandbox session paths are host-readable. This is a boundary to verify, **not a demonstrated failure**.

## 9. Follow-up: sandbox-only skills, menu discovery, and the filesystem/RPC boundary

### Answer and limits

**At this pinned stock Orca commit, sandbox-only Pi skills can appear in an acquired Chat session's `/` menu and be invoked without copying their skill files to the host.** This is conditional on the sandbox Pi actually loading them and successfully completing RPC startup. The menu's authoritative session catalog comes from **`get_commands`**, not solely from Orca's host skill scan. This is a source-supported capability, **not a reproduction of the user's setup or a diagnosis of their failed attempt**. A skill “executes” here by loading instructions for the model; scripts mentioned by those instructions still need working tools/dependencies and permissions in Pi's execution environment.

Do not conflate these three mechanisms:

| Mechanism | Owner / filesystem | Consequence for sandbox-only skills |
| --- | --- | --- |
| Pi automatic discovery and model use | The Pi child, using its effective agent directory, cwd, settings, packages and trust state | Skills can be advertised to and read by the model inside the sandbox, independently of Orca's host skill catalog. |
| Orca Skills management / disk discovery, and composer fallback before a session catalog exists | Orca execution host's filesystem (with explicit separate native/WSL discovery support) | An arbitrary `sbx` wrapper does not automatically make its private skill tree visible to this scanner. |
| Acquired Pi Chat composer menu | Pi RPC `get_commands` → Orca session command state → renderer | Reported skills can produce menu rows even with **no matching host file**. |

### Pi discovery is local to the Pi process, not local to the Orca renderer

Installed Pi **1.6.0** primary docs `docs/skills.md:41–63` say startup advertises names/descriptions/paths, the model reads the skill when appropriate, `/skill:name` forces loading, and `.agents/skills` has user and ancestor-project locations. `disable-model-invocation: true` hides a skill from automatic selection, not explicit invocation. Source `dist/core/skills.js:278–300` filters those hidden skills and formats the rest into the model prompt with their file locations. Invalid skills and name collisions can also affect availability (`docs/skills.md:79–85`). These facts are about the installed investigation package, not an unverified sandbox version.

In that package, `dist/core/package-manager.js:763–780,2174–2239` builds skill locations from **`<agentDir>/skills`**, project `.pi/skills`, home `.agents/skills`, and ancestor-project `.agents/skills`; project discovery is trust-gated at lines 2199–2223. `dist/core/resource-loader.js:441–450,645–656` merges configured and explicit skill paths and checks explicit paths in Pi's filesystem. `docs/cli.md:202–205` documents repeatable `--skill` and that `--no-skills` still allows explicitly supplied paths. Thus “installed inside the sandbox” alone does not guarantee discovery: location, effective cwd/agentDir, trust/settings, validity and duplicate names matter.

#### `PI_CODING_AGENT_DIR` can change which sandbox skills are discovered

Orca resolves its selected account home from launch env `PI_CODING_AGENT_DIR` or **host** `homedir()/.pi/agent` [`src/main/pi/rpc-runtime-metadata.ts:40–44`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc-runtime-metadata.ts#L40-L44), then explicitly sets `env.PI_CODING_AGENT_DIR = deps.accountDir` when resolving the Pi invocation [`src/main/pi/rpc/launch/rpc-launch-resolution.ts:125–136`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch-resolution.ts#L125-L136). Installed Pi reads that variable **before** falling back to its own home `.pi/agent` (`dist/config.js:489–515`; SDK selects the default agentDir at `dist/core/sdk.js:71`).

**Conditional implication:** if `sbx` forwards this host-valued variable unchanged, sandbox Pi uses that path (as interpreted inside the sandbox), **not necessarily sandbox `~/.pi/agent`**. It might point to a mounted host tree, an unrelated/missing sandbox path, or a path intentionally translated by the wrapper/runtime. If forwarding strips the variable, Pi falls back to sandbox home; if it remaps it, the mapped directory wins. This investigation has **not established `sbx`'s env forwarding or translation**, so none of those outcomes is asserted as observed. Changing the agentDir does not in itself disable the separate home `.agents/skills` or project discovery paths above.

Likewise Orca's process-spawn cwd is a host workspace/pinned directory (§4–6), but the effective cwd of sandbox Pi is determined by the wrapper/runtime. Project skill discovery follows **Pi's effective sandbox cwd and ancestors**, not merely the host path shown in Orca. Neither matching cwd/mount paths nor sandbox project trust was verified.

### `get_commands` really is a skill-menu input; paths are not required on this Pi route

1. Installed Pi RPC handles `get_commands` by enumerating extensions, prompt templates and **all loaded skills**. Skills are returned with `name: skill:<name>`, description, `source: skill`, and `sourceInfo` (`dist/modes/rpc/rpc-mode.js:554–580`). This handler does not test `enableSkillCommands`; do not apply the documentation's *interactive command discovery* setting indiscriminately to this RPC handler.
2. Orca's schema accepts name/description/source; `readPiRpcCommands` maps `source === 'skill'` to `kind: 'skill'` and retains name/description. 3. ### Timing: no pre-chat Pi skill RPC probe was found

Pi's startup first requests `get_state`, establishes the session link and catches up history [`src/main/pi/rpc/rpc-session-startup.ts:43–93`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/rpc-session-startup.ts#L43-L93). Therefore skills may arrive **after** the child/session opens and after the preceding options read; merely seeing a chat tab does not establish that this stage completed.

The Pi adapter's `readCommands(id)` only returns `sessions.get(id)?.startup.commands` [`src/main/pi/rpc/rpc-session-adapter.ts:206–208`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/rpc-session-adapter.ts#L206-L208). Its registration constructs the adapter without an at-rest command catalog [`src/main/pi/rpc-runtime-registration.ts:15–56`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc-runtime-registration.ts#L15-L56). Shared command reads use live data first, otherwise an **optional** at-rest provider [`src/main/native-chat/agent-session-wire/options/structured-agent-session-command-reads.ts:7–18`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/native-chat/agent-session-wire/options/structured-agent-session-command-reads.ts#L7-L18). In this Pi implementation, a fresh, unacquired tab has no sandbox `get_commands` catalog; host filesystem fallback may still provide menu entries. **An acquired RPC child is needed to obtain sandbox-only menu data initially**; opening the menu does not itself demonstrate a separate sandbox skill-listing process. Already received command data is cached on session/renderer state; this trace does not promise every previously rendered row disappears immediately on child shutdown. Invocation needs a successfully usable Pi child (including reacquisition if applicable). The standalone pre-chat model catalog probe in §5 reads state/models, **not `get_commands`**.

### Selecting/sending a skill is not the host reading `SKILL.md`

The Pi profile uses slash sigil plus `skill:` prefix [`src/shared/native-chat/input/commands/native-chat-agent-profiles.ts:84–89`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/shared/native-chat/input/commands/native-chat-agent-profiles.ts#L84-L89). Host-owned slash controls are a separate recognized set [`src/shared/agent-session/view/structured-agent-session-composer.ts:85–98`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/shared/agent-session/view/structured-agent-session-composer.ts#L85-L98); Pi skill commands are agent text, not a host file expansion.

Installed Pi expands text beginning **`/skill:name`** by resolving that name against its loaded skill list and reading `skill.filePath` **inside the Pi process**, stripping frontmatter and adding its base directory and optional trailing arguments (`dist/core/agent-session.js:1820–1842`; queued input also expands at 1852). Missing names/read failures leave the original text instead of proving the skill ran. Plain `/<name>` is not this expansion. The model can also read a normally advertised skill without the user selecting any menu row. Both routes use sandbox-readable files/tools when Pi and its tools run there; neither requires Orca to read that skill file first.

### Boundary: not all paths crossing RPC are alike

- **Skill catalog:** names/descriptions/source are sufficient. At this Orca/Pi route the skill path metadata is discarded; no host skill-file existence requirement is evidenced.
- **Host skill browser/scanner:** the native scanner canonicalizes and reads discovered files on its own host [`src/main/skills/discovery/skill-native-discovery.ts:115–138`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/skills/discovery/skill-native-discovery.ts#L115-L138), including a home Pi root [`src/main/skills/discovery/skill-discovery-sources.ts:176–183`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/skills/discovery/skill-discovery-sources.ts#L176-L183). Target discovery explicitly branches native versus WSL [`src/main/skills/discovery/skill-discovery-target.ts:183–218`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/skills/discovery/skill-discovery-target.ts#L183-L218). This does not imply arbitrary `sbx` filesystem access or a `get_commands`-backed global Skills page.
- **Injected resources:** Orca obtains visuals/linked skill directories and passes repeatable **`--skill <path>`** [`src/main/pi/rpc/launch/rpc-launch-resolution.ts:202–208`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch-resolution.ts#L202-L208) [`src/main/pi/rpc/launch/rpc-launch.ts:180–191`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch.ts#L180-L191). These add resources; they do not turn Orca's host discovery into a requirement for every Pi skill, and do not themselves suppress Pi defaults. Those paths (and host instructions/extensions) must be meaningful to sandbox Pi to load them; the wrapper's mount/translation behavior is unknown.
- **Session paths:** not interchangeable with skill metadata. Orca validates returned session paths as absolute and against resume/fork expectations [`src/main/pi/rpc/launch/rpc-launch-resolution.ts:286–301`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/rpc-launch-resolution.ts#L286-L301). It also has actual **host file reads** for session header/resume decisions [`src/main/pi/rpc/launch/pi-session-header.ts:11–31`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/launch/pi-session-header.ts#L11-L31) and session tail hints [`src/main/pi/rpc/history/rpc-session-file-tail.ts:8–22`](https://github.com/stablyai/orca/blob/a91fc0a676e324b2630a78bdc6d885f513cc9d88/src/main/pi/rpc/history/rpc-session-file-tail.ts#L8-L22). This disproves “all returned paths are opaque RPC identifiers.” It does **not** prove every session path must already host-exist at initial `get_state`: the link validator shown checks shape/identity, whereas later file operations have their own behavior/errors. No general host path mapping is supplied by JSONL itself.

**Still unknown:** user's actual Pi/Orca versions; effective sandbox env/HOME/cwd/accountDir; project trust; installed skill locations/settings; whether RPC startup reached the post-open catalog read; returned `get_commands`; any command-read warning; whether injected resources/session files are shared or translated. These distinguish “not in Orca's global Skills page,” “not loaded by Pi,” “catalog not received yet,” and “skill listed but invocation/tools failed.” The reported experience alone cannot distinguish them.

## 10. Follow-up: returning npm's latest Pi version is not an installed-version probe

**It can satisfy Orca's semver parser, but it is not a correct answer to `pi --version` for the sandbox executable.** Installed Pi prints its own package `VERSION` (`dist/main.js:545–547`; `dist/config.js:493` uses `pkg.version`). Registry `latest` is a registry package/tag version, not evidence about an already installed sandbox binary, which could be pinned, cached, older, modified or a different package. A synthetic latest version can falsely pass Orca's minimum RPC gate or advertise version-gated features the sandbox does not implement (§3: `--no-mcp`, image shrinking assumption). It also says nothing about whether the actual RPC child can start or discover skills.

Local npm **9.2.0** source cross-check (`/usr/share/nodejs/npm/package.json:2`; read only; no npm command executed): `/usr/share/nodejs/npm/lib/commands/view.js:187–207` requests a package **packument** and resolves its dist-tag; this is not inspecting the sandbox executable/package. That local npm version sets `preferOnline: true` at line 190. `/usr/share/nodejs/npm/lib/utils/config/definitions.js:1540–1548` documents that prefer-offline skips cache staleness checks but may fetch missing data; lines 1378–1385 describe forced offline mode. These are illustrative local primary-source semantics, **not proof of the user's exact workaround command, npm version or config**.

Consequences, conditional on how the workaround is written:

- A registry lookup on each version call adds network/DNS/registry availability and latency to a nominally local check; it can still exceed Orca's ordinary 5-second probe budget. Catalog probing removes that local timeout (§3), which is not a guarantee that registry access is fast or succeeds.
- Offline or cached metadata can be unavailable or stale; “cached latest” is neither necessarily today's registry latest nor the installed sandbox version. Prefer-offline is not a guarantee of no network. A cached/hard-coded wrapper response avoids live lookup only if the wrapper actually uses it, and its truth depends on how it is tied to the sandbox installation/version updates.
- Querying metadata need not create a sandbox, but does not address the **separate home-cwd RPC model probe** (§5). Avoiding unrelated provisioning is a wrapper/runtime policy boundary for that invocation too, not solved merely by special-casing `--version`.

No implementation, wrapper/kit changes, npm network scripts, Pi launches or sandbox provisioning were performed for this follow-up. Existing TUI behavior was not changed or tested. The research establishes stock-Orca capability and boundaries, not a validated integration design.

### Lifecycle caveats and truthful version reporting

`exec` runs foreground, returns the command's exit status, returns 125 if it cannot run it (e.g. missing sandbox), and local missing executable returns 127. It **starts a stopped sandbox first**; it does not document creating a missing one. Consequently “no create” is not “no startup”: exec can still start the VM/container and kit startup work. See [exec reference](https://docs.docker.com/reference/cli/sbx/exec/) and [CI guide:55–69](https://github.com/docker/docs/blob/77d9d8c048d0743a0e9d4bc3878a87106c66e495/content/manuals/ai/sandboxes/workflows/automation.md#L55-L69).

Installed Pi 1.6.0 `docs/rpc.md:89–95` says stdin EOF and SIGTERM initiate orderly Pi shutdown. **Whether closing/killing the host sbx client delivers EOF/SIGTERM to remote Pi, drains output, waits for exit or leaves descendants is not established by the reviewed sbx docs.** Exec has no detached mode, but this does not prove cancellation propagation. Orca's host-process termination barrier cannot by itself prove remote exit. Validate before allowing reacquisition/retry to create another RPC owner. Exact stdin/stdout separation, prompt-free failure and absence of injected text also need a live test.

For an existing sandbox, **`sbx exec NAME -- pi --version`** bypasses kit agent launch/defaults, but still loads Pi's CLI. Installed `dist/main.js:510–547` performs some configuration/proxy initialization before its version branch exits; “does not enter TUI/RPC” is safer than “does no startup.” To avoid **Pi application startup altogether**, exec an explicit filesystem/JSON reader (e.g. Node), resolve the actual selected `pi` symlink and read its owning **`@earendil-works/pi-coding-agent/package.json` version**, without importing Pi. Do not hard-code an npm prefix or `dist` depth: local 1.6.0 `package.json:9–11` points `pi` at `dist/bundle/cli.js`. The upstream image [Dockerfile:101–111](https://github.com/docker/sbx-kits-contrib/blob/c279c9da843e51b135a5be3750ffcdf8078485b4/pi/Dockerfile#L101-L111) creates `/usr/local/bin/pi` from the build's npm prefix. Metadata identifies that installed package, not proof it executes successfully; alternate PATH binaries/wrappers must be accounted for. These are diagnostic/design options, not an implemented probe.

### Image metadata, pinning and offline strategy

- Pi is **baked in at image build**, not fetched afresh on every version probe. The image defaults to `PI_VERSION=latest`, fetches npm's package-version document into `/tmp/pi-latest.json`, installs that resolved version, and runs `pi --version` as a build gate ([Dockerfile:47–64](https://github.com/docker/sbx-kits-contrib/blob/c279c9da843e51b135a5be3750ffcdf8078485b4/pi/Dockerfile#L47-L64), [98–104](https://github.com/docker/sbx-kits-contrib/blob/c279c9da843e51b135a5be3750ffcdf8078485b4/pi/Dockerfile#L98-L104)). Nightly rebuilds track npm latest; an explicit **build argument** can pin Pi. Pinning only the kit Git commit/tag leaves its `sandbox.image: …:latest` floating ([upstream README:103–128](https://github.com/docker/sbx-kits-contrib/blob/c279c9da843e51b135a5be3750ffcdf8078485b4/pi/README.md#L103-L128)).
- Public [latest-tag API](https://hub.docker.com/v2/repositories/sbx/pi-image/tags/latest) returned index digest **`sha256:f09d9e4c3f1124b13234b66bda14bca3e2a5ff29c93c6c6afd6ae42f25d64cac`**, pushed `2026-11-25T05:36:20.624535Z`, with linux amd64/arm64 manifests. [Tag listing](https://hub.docker.com/v2/repositories/sbx/pi-image/tags?page_size=10) also returned `20261125-c279c9da843e51b135a5be3750ffcdf8078485b4` at that digest. ## 12. Before the first message: acquisition routes, shared skills, and refresh limits

### Requirement and corrected conclusion

The requirement is now **skills visible before the first message**, not eventual visibility after sending. A context-free temporary discovery sandbox is acceptable only if skills subsequently installed in the real project's sandbox also remain discoverable. This supersedes §11's unresolved Q6; do not treat delayed visibility as accepted.

**There are two source-supported ways to meet pre-message visibility without changing Orca source:** (1) put the authoritative skill files in a host-visible, Pi-readable shared discovery root; or (2) launch a **new** Pi Chat using stock Orca's **no-prompt CLI launch**, which takes the acquired compatibility path at this pin. The second is a different entry point from opening a normal fresh UI Chat, not a setting that makes ordinary UI creation eager. Both remain conditional on successful discovery/startup and the wrapper/runtime boundary in §11. Neither was executed here.

**Do not recommend `agentSession.ensure` for Pi.** Its generic internal attach machinery can acquire before any message, but its *public wire schema* only accepts Claude/Codex provider/account/handle forms. That distinction prevents a misleading inference from the internal acquisition function. Likewise a command-menu “refresh” is not necessarily a new Pi `get_commands` request.

Evidence scope: same Orca commit `a91fc0a676e324b2630a78bdc6d885f513cc9d88`, locally inspected in `/tmp/orca-investigation.r3tw7h`; same installed Pi **1.6.0** source/docs as §8–9; Docker documentation already downloaded for §11. No source/wrapper/kit change, Pi child, sandbox, authenticated API call, credential access, or live integration test. References below distinguish public interfaces from internal code.

### 12.1 What actually starts Pi before a message?

| Action | Pinned behavior / implication |
| --- | --- |
| Open a **fresh normal UI Chat**, with no opening message | Renderer advertises the create-message capability. Create chooses at-rest founding: `spawnToken` throws `founding_must_not_reserve_a_spawn`, and without `firstMessage` founding commits the record/journal, not a provider owner. This does **not** obtain sandbox skill RPC data. [A1–A3] |
| Open/view/reconnect the chat subscription | `agentSession.subscribe` explicitly says a stream reads and never starts or keeps an agent alive. A renderer/network reconnect is not evidence of provider reacquisition. [A4] |
| Open `/` / the command picker, retry command discovery | UI issues `agentSession.commands`, whose host command reader returns live adapter commands or an optional at-rest catalog. Pi's adapter exposes cached startup commands and has no registered at-rest catalog (§9). No Pi owner is acquired on this path. A separate host skill scan can run. [A5–A7] |
| Explicit “connect/acquire” button or slash command for an untouched Pi Chat | No such stock UI/CLI action was established: full source search finds `agentSession.ensure` registration/allowlist/tests, **no renderer or CLI invocation**. More decisively its strict public `AttachParams` requires `provider: codex|claude`, matching handle and account-home forms; attach admission requires agent = provider. It cannot be repurposed as `agent: pi` by supplying a Claude handle. [A8–A9] |
| Internal `host.attach` / `performAttach` | Can acquire independently of a message: absent a retained live owner/replayed successful operation, calls `acquireOwner`, then publishes hydration. This proves acquisition is **not intrinsically message-dependent**, but is not itself a public Pi connect command or authorization mechanism. [A10] |
| Stock CLI launch, **new** Chat, no `--prompt` | Supported alternate entry point below: current CLI lacks the UI's create-message capability, so no-prompt launch reaches `host.attach` and acquires before any prompt. [A11–A17] |
| Command prefix/Arguments/env configuration | Configures the program/argv/environment **when invoked**, not the host's create/subscribe/menu policy. No eager-acquire setting was found in this path. Prefix `--skill` can change what a started Pi loads, but cannot make an at-rest UI tab execute the wrapper. A `--version`/model-catalog invocation is a different child; no skill-catalog handoff from it is implemented. [A1–A7, A18; §5, §9] |

A source-backed negative here means “not offered by the inspected stock path,” **not** “Pi RPC cannot exist before a first message.” Opening an existing already-acquired chat can of course display its existing command catalog; that does not solve an untouched fresh tab.

### 12.2 Supported no-prompt CLI launch: exact scope, arguments and access

Illustrative supported command shape (the selector is a **flag value**, not a positional path):

```console
orca agent launch --agent pi --surface chat --worktree '<exact-worktree-selector>' --focus --json
```

**Omit `--prompt` entirely.** Do not send a dummy message or assume an empty positional argument is a no-message request. Orca's help source lists `agent launch --agent <id> [--worktree <selector>] [--prompt <text>] ... [--focus] [--json]`; flag help documents `--surface chat|terminal`. Parser accepts only these surface values, requires `--agent`, and only creates a prompt object for a supplied nonblank string `--prompt`. The handler resolves the supplied `--worktree` selector using `getRequiredWorktreeSelector`; remote CLI requires this flag explicitly. It targets `{kind:'existing', worktree}` and `--focus` controls presentation, **not** prompt delivery. [A11–A12, A19]

Why it acquires, rather than merely opening another resting record:

1. With no prompt, `launchPromptCreateInputs` returns `{}` (no `firstMessage`); executor adds `withoutPrompt: true`. [A13]
2. Surface factory's `atRest` is true only if a `firstMessage` exists, or `withoutPrompt` **and** the caller advertises `AGENT_SESSION_CREATE_MESSAGE_RUNTIME_CAPABILITY`. Stock paired CLI capability list omits this capability; local CLI socket requests carry no `clientCapabilities` field, and host comments explicitly identify CLI/runtime-socket callers as lacking it. UI's list, in contrast, includes it. [A1, A14–A15]
3. Thus for this no-prompt CLI launch `atRest` is absent. Worktree create-intent resolution constructs the **Pi** internal attach params, rather than asking CLI to supply the restricted public `AttachParams`. `commitStructuredAgentSessionCreate` takes `prepared.host.attach(...)`, whose flow acquires the owner before returning/publishing the completed surface. This is the supported compatibility path, not a forged `ensure` request. [A10, A16–A17]
4. Successful Pi acquisition schedules `reportAfterOpen`: options/model listing first, then `readCommands` (`get_commands`), caches commands and publishes. **No prompt is required for that scheduled read.** It is asynchronous: acquisition/CLI return does **not** guarantee that the skill list is already displayed. A listing read can delay it; ordinary listing errors are caught, but startup failure, closed connection, or other report failure can leave commands unavailable. Wait for the actual catalog/menu result, not just a tab or CLI receipt. [A6, A20]

This starts a **new chat in an existing workspace**; it is **not** an existing-chat `connect`, does not upgrade an already-open untouched UI chat, and is not “one click Connect” in the ordinary composer. It leaves the user launching chats through CLI (or an independently chosen launcher), then using their Orca UI before typing the first message. Replaying a recorded launch is not an instruction to restart a dead owner. Inspect `outcome.kind`/receipt: `--surface chat` is not a blanket guarantee against all runtime fallbacks/failures (§6 and CLI guide).

**Access is the existing stock CLI's access, not a guessed wrapper credential scheme.** `agent.launch` is a registered workspace-permission method; the stock local transport discovers the runtime endpoint, checks trusted socket-directory ownership, and sends the metadata auth token through its normal request framing. Paired CLI uses its configured paired connection. Use an already working authorized Orca CLI on the execution host/selected environment; there is no evidence that a Pi wrapper automatically has this socket, metadata or remote credential access inside an arbitrary sbx. Nothing here recommends reading tokens, manufacturing RPC envelopes, or calling back into Orca from a wrapper's version probe. [A15, A21] This route is **compatible with keeping wrapper-only integration changes out of Orca**, but changes the user's chat-launch workflow; no wrapper change was made or designed here.

### 12.3 Pre-session host fallback: computed roots, not sandbox env

Before a Pi catalog is reported, `nativeChatSessionSkills` returns `undefined`, preserving the disk scan; once Pi reports even an empty command array, Pi's session-reported skill list becomes authoritative, not a permanent union with host skills. Pi profile reads its own roots plus shared owner-null roots. [A22]

The picker starts `useNativeChatSkills` when its skill trigger is active. Its context is the pane startup/pinned directory (or launch workspace), owning execution host/runtime, and project-runtime key; it calls `skills.discover` with `{cwd, worktreeId, ...}`. A cwd-targeted native scan passes **`repos: []`**, not every registered project's repositories. Roots come from `buildSkillDiscoverySources`: host home `.agents/skills`, **host home `.pi/agent/skills`**, cwd `.agents/skills`, plus other provider roots filtered by Pi's source ownership. This scanner does **not** mirror Pi's entire ancestor/package/settings/trust discovery algorithm, nor discover arbitrary sandbox paths. In particular the hard-coded Pi home source is not relocated by launch `PI_CODING_AGENT_DIR`, and this source builder has no project `.pi/skills` entry. [A23–A25]

**Configuration boundary:** source-builder `homeDir`, `cwd`, `providerRootOverrides` parameters are internal API inputs, not evidence of a user “Pi skill directories” preference. Runtime override computation uses `process.env` and the install-provider table's `homeEnv` entries (e.g. Claude/Grok/Kiro); Pi's discovery-only home source is separately hard-coded. Changing Pi's configured command env/`PI_CODING_AGENT_DIR` affects child discovery (§9), **not this host scanner**. No stock arbitrary Pi fallback-root setting was established. Do not suggest changing the application's whole HOME just to relocate skills. [A24, A26]

Host scan refresh is real: each picker reopen asks again, retains last good per-pane answer during the read, and explicit Retry forces a refreshed scan; failures can preserve a last-good list. It does not hot-refresh an independently running Pi's loaded skills, and after live Pi reports skills a host-only new entry is not sufficient to establish session availability. [A23, A22]

### 12.4 Shared mounts: one authoritative installation is feasible; reverse export is not automatic

**Supported single-source arrangement:** have skill installations performed *inside Pi's sandbox* write to the **already bind-mounted actual project's `.agents/skills/<name>/SKILL.md`**, so the same files are host-discovered before any message and Pi-discovered in the real project. Or use a deliberately shared host-backed home skill tree that both processes actually discover. These are shared authoritative files, not two independently maintained installations. Host-native discovery reads/canonicalizes the files on its own filesystem; permissions, metadata validity, path/depth limits and Pi trust/discovery must still succeed. The menu is refreshed by reopening/retrying the host scan. Pi's resources must be loaded/reloaded separately if already running. [A23–A25, A27; §9]

Docker documents directly mounted workspace paths (default same absolute path), additional workspace `PATH:TARGET[:ro]`, and that extra workspaces are direct mounts even with clone mode. Therefore writing new skills into such a **writable host-backed mount** inside the project sandbox makes the same files visible on the host without a maintained copy. The primary workspace needs no extra target mapping for `.agents/skills`. Avoid `--clone` for that primary-file-sharing claim: the primary becomes a separate clone; mount a separate shared skill directory if needed. Additional mount targets cannot be reserved skills paths, primary path, or certain clone paths—do not assert that mapping directly over a reserved in-sandbox skills directory is accepted. Use a documented ordinary shared project path or separately verify the chosen target. [D1]

**What this does not do:** turn existing skill files in a sandbox's private home/image/volume into host files. Documented additional mounts take a **host source**, not `SANDBOX:/private/path` as a reverse-mounted host discovery root. V2 `volumes` are container block/tmpfs paths, not a host-export interface. A host symlink to a path only present inside the VM is still unreadable to the native scanner. A one-time migration into an agreed shared authoritative tree could eliminate future duplicate maintenance, but is a separate user decision; no such migration is performed. Reattaching today's wrapper does not document changing existing sandbox mounts. [D1–D2; §11]

This also preserves skills installed later in the **actual project sandbox**, **only if those installations use its shared discoverable tree**. If a later installer defaults back to private `~/.pi/agent/skills`, neither a temporary discovery sandbox nor the host scan sees that new file automatically. “Mount something” without controlling the authoritative install destination is not a complete solution.

### 12.5 Installing skills later: Pi reload, `get_commands`, and Orca menu refresh are different

Installed Pi 1.6.0 evidence (paths relative to the package root in §8):

- **`get_commands` is a read of currently loaded resources**, not a filesystem rescan: `dist/modes/rpc/rpc-mode.js:554–580` enumerates registered extension commands, `session.promptTemplates`, and `session.resourceLoader.getSkills().skills`. Creating a new `SKILL.md` alone does not make that cached resource loader rediscover it.
- **Interactive `/reload` exists**: `dist/modes/interactive/interactive-mode.js:2807–2810` intercepts it and calls its reload UI handler. Core `dist/core/agent-session.js:3104–3141` rejects reload during streaming/compaction, reloads settings/resources, rebuilds runtime, and emits reload boundary events. That operation can refresh loaded skills in that **same process**.
- **Stock RPC has no `{type:'reload'}` handler** (switch falls to Unknown command at `dist/modes/rpc/rpc-mode.js:582–584`), nor a built-in `/reload` interception in `session.prompt`. Prompt only dispatches registered extension commands first, then ordinary prompt processing (`dist/core/agent-session.js:1698–1721,1791–1814`). Consequently sending `/reload` via RPC is **not equivalent** to TUI `/reload`; absent a registered extension command it can become model input. Do not send it as a magic no-message connect/refresh operation.
- RPC **does expose reload to an extension command context** (`dist/modes/rpc/rpc-mode.js:250–274`: `reload: async () => await session.reload()`). `docs/extensions.md:1514–1538` documents `ctx.reload()` and a registered `reload-runtime` example. Thus a previously installed appropriate extension can reload resources through RPC command handling; this is **not** stock RPC reload or an Orca UI control. After an actual same-process reload, a subsequent `get_commands` enumerates the new loaded skill list. Reloading another TUI Pi process does not mutate Orca's separate child.

**Pinned Orca does not reissue Pi `get_commands` when the menu says refresh.** The only call site of Pi startup's private `readCommands` is `readAfterOpen`, and `PiRpcSessionAdapter.readCommands` returns `startup.commands` without transport I/O. Menu open performs `agentSession.commands`; menu-query invalidation/subscribed command changes can requery the host, but host returns the live cached adapter value first. Therefore a new skill can remain absent even after a custom in-process Pi reload and a menu reopen, unless Orca itself obtains a fresh Pi catalog—which this adapter has no exposed refresh hook to do. [A5–A7, A20, A28]

A **new actual Pi acquisition** creates the startup reader again and schedules fresh `get_commands`, subject to startup/listing failures above. A UI/network reconnect to an existing live child merely resubscribes and reads its cached commands; a new chat under the supported no-prompt CLI route is a concrete pre-message reacquisition route. Do not promise “reload the window,” “reopen the menu,” “retry commands,” or “reconnect session” means respawn. No verified stock UI-only pre-message restart/refresh action for an untouched Pi tab was found. [A4–A7, A10–A20]

### 12.6 Temporary discovery sandbox and project catalog isolation

The ordinary context-free Pi model probe reads state/models, **not `get_commands`** (§5, §9). Provisioning a temporary sandbox for it does not feed that sandbox's skills into a fresh project's slash menu. Adding skills later in a separate real project's private sandbox likewise cannot update either that temp child's resources or a host disk scan. No stock cross-sandbox skill aggregation/synchronization is evidenced.

A shared global host-discovered skill root can deliberately make one authoritative catalog visible to many sandboxes before messages, but then **all projects may see that shared catalog**: that is global scope, not per-project discovery. If project-specific skills are installed there, other projects can see names they cannot actually execute/read unless the files and dependencies are shared there too. Same-name skills also introduce Pi's existing collision rules (§9). One long-lived temp child's `get_commands` is its own cwd/account/settings/trust-loaded catalog, not authoritative for every project's real sandbox.

Conversely project `.agents/skills` plus the per-pane cwd-targeted scan avoids a global union: cwd scans supply `repos: []`, renderer keys cache by host/runtime/cwd, and scans are filtered by source ownership. Host-global roots still remain global; and pre-session scanner coverage can differ from Pi's ancestor discovery. The strongest source-supported isolation option here is **project-specific shared authoritative skill files**, or actual per-project acquisition (the no-prompt CLI route), not caching one discovery sandbox's command list for all projects. [A22–A25]

**Decision boundary:** (a) accept CLI-based creation of each new eagerly acquired Chat, or (b) keep normal UI creation and put actual project skill installations into a shared host-discovered root. If neither workflow is acceptable and skills must remain exclusively private to an unacquired project's sandbox, the inspected stock UI/config/mount paths do not establish a solution. This is not a request to implement either path, and all sbx RPC transport/termination checks in §11 remain outstanding.
